# Локальное сохранение изменений мероприятий

## Контекст

При создании или редактировании мероприятия сетевой сбой после нажатия "Создать" или "Применить" приводит к ошибке, а модалка уже закрыта. Пользователь теряет контекст формы и вынужден вводить данные заново.

Текущий поток:

- форма мероприятия находится в `layouts/modals/modalsFunc/eventFunc.js`;
- сохранение вызывает `itemsFuncAtom.event.set`;
- сетевой запрос выполняется через `helpers/CRUD.js`;
- локальное обновление списка выполняется через `eventEditSelector`;
- серверная запись идет через `/api/{location}/events` и `/api/{location}/events/{id}`.

Задача соответствует roadmap-направлению `STATE-T6`: постепенно выносить CRUD-логику из Jotai в доменные actions/hooks.

## Цель

Сохранять данные создания и редактирования мероприятия в локальной памяти браузера до успешного ответа сервера, чтобы пользователь мог повторить отправку после временного сбоя сети.

## Область реализации

В первый релиз входит только создание и редактирование мероприятий:

- `create` для нового мероприятия;
- `update` для существующего мероприятия;
- автоматическая повторная отправка при восстановлении сети;
- ручная повторная отправка через UI;
- удаление успешно отправленной операции из локальной очереди.

В первый релиз не входит:

- удаление мероприятий;
- очередь для пользователей, платежей, услуг и других сущностей;
- offline-first синхронизация с разрешением конфликтов;
- фоновая синхронизация через service worker.

## Хранилище

Используется `localStorage`, потому что payload мероприятия уже сериализуемый JSON и не содержит файловых blob-объектов. Фотографии в форме хранятся как ссылки/метаданные после загрузки через существующий `InputImages`.

Ключ:

```text
polovinka:pending-event-mutations:v1
```

Формат записи:

```json
{
  "id": "local unique id",
  "operation": "create",
  "location": "krsk",
  "eventId": null,
  "payload": {},
  "createdAt": 1782943200000,
  "updatedAt": 1782943200000,
  "attempts": 0,
  "lastError": null,
  "status": "pending"
}
```

Для редактирования:

```json
{
  "operation": "update",
  "eventId": "mongo id"
}
```

## Поведение

Перед сетевым запросом клиент кладет операцию в локальную очередь. После успешного ответа сервера операция удаляется.

Если запрос падает из-за сети, timeout, недоступности сервера или ответа без успешного результата, операция остается в очереди со статусом `failed`. Пользователь видит snackbar: "Изменения сохранены локально. Повторим отправку, когда связь восстановится."

При событии `window.online` и при загрузке клиентского приложения очередь пробует отправить операции текущей локации. Для пользователя также доступна ручная кнопка "Повторить".

Если пользователь несколько раз редактирует одно и то же мероприятие до синхронизации, новая операция `update` для того же `location + eventId` заменяет предыдущую. Для `create` каждая операция остается отдельной, чтобы случайно не потерять два разных новых мероприятия.

## UI

Добавляется небольшой клиентский индикатор в общий слой приложения:

- если очередь пуста, ничего не показывается;
- если есть операции, показывается компактный блок "Есть несохраненные изменения мероприятий";
- рядом показываются кнопки "Повторить" и "Сбросить";
- "Сбросить" удаляет локальные операции только после подтверждения.

Индикатор не должен блокировать работу приложения и не должен открывать модалку автоматически.

## Ошибки и безопасность

Клиентская очередь не считается источником истины. Сервер остается единственным источником данных.

Если сервер возвращает валидную бизнес-ошибку, например запрет управления городом или ошибку валидации, операция остается в очереди, но получает `lastError`. Автоматические повторы ограничиваются, чтобы не создавать бесконечный цикл. Пользователь может открыть ошибку и решить, повторять или сбросить запись.

В локальную очередь не записываются секреты, токены и данные окружения. Payload содержит только те данные мероприятия, которые пользователь уже вводит в форму.

## Тестирование

Проверить:

- успешное создание удаляет операцию из очереди;
- успешное редактирование удаляет операцию из очереди;
- сетевой сбой оставляет операцию в очереди;
- повторная отправка вызывает нужный endpoint;
- редактирование того же мероприятия заменяет старую pending-update операцию;
- разные create-операции не затирают друг друга.

Минимальный ручной smoke:

- открыть форму мероприятия;
- внести изменения;
- отключить сеть в DevTools;
- нажать "Применить";
- убедиться, что появился индикатор pending-изменений;
- включить сеть;
- нажать "Повторить" или дождаться авто-повтора;
- убедиться, что изменение появилось на странице.
