# Технические решения (ADR-lite)

Формат:
- `Статус`: accepted/superseded/proposed
- `Контекст`: что решали
- `Решение`: что выбрали
- `Последствия`: trade-offs

## ADR-001: Гибридный роутинг `app/` + `pages/`
- Статус: `accepted`
- Контекст: проект содержит одновременно новый UI-контур и legacy API/страницы.
- Решение: сохранить гибрид, не делать "big bang" миграцию.
- Последствия:
  - плюс: стабильность продакшена и постепенная миграция
  - минус: повышенная сложность навигации по коду

## ADR-002: Мульти-локация как базовый инвариант
- Статус: `accepted`
- Контекст: продукт работает в нескольких городах и расширяется.
- Решение: не допускать одногородских правок без явного согласования.
- Последствия:
  - плюс: переносимость функционала
  - минус: больше проверок при изменениях

## ADR-003: `GlobalUsers` для мягкой межгородской связки
- Статус: `accepted`
- Контекст: один пользователь может участвовать в нескольких городах.
- Решение: выделить глобальную сущность пользователя + `cityProfiles`.
- Последствия:
  - плюс: меньше дублей, лучше межгородской UX
  - минус: усложнение auth и миграционных сценариев

## ADR-004: Guard-слой городских операций
- Статус: `accepted`
- Контекст: требуется закрытие/архивация города без потери истории.
- Решение: централизованный guard (`getCityPolicy`, `assertCityOperationAllowed`).
- Последствия:
  - плюс: единая точка контроля ограничений
  - минус: нужно следить за покрытием guard в новых API

## ADR-005: API-ответы в едином envelope
- Статус: `accepted`
- Контекст: разные endpoint’ы исторически возвращают данные неоднородно.
- Решение: для новых/изменяемых API придерживаться:
  - успех: `{"success": true, "data": ...}`
  - ошибка: `{"success": false, "data": {"error": {"type": "...", "message": "..."}}}`
- Последствия:
  - плюс: предсказуемый клиентский код
  - минус: требуется технический долг по старым endpoint’ам

## ADR-006: Сценарии пользователя через модалки как системный паттерн
- Статус: `accepted`
- Контекст: критические действия (запись, подтверждения, редактирование) завязаны на UI-модалки.
- Решение: оставить `state/modalsFuncAtom.js` как центральный оркестратор модалок.
- Последствия:
  - плюс: единообразный UX и централизованные guard-проверки на клиенте
  - минус: высокий риск регрессий при точечных правках

## ADR-007: TELEFONIP как эталонный канал phone verify
- Статус: `accepted`
- Контекст: телефон — ключевой идентификатор в credential-сценариях.
- Решение: использовать `docs/TELEFONIP_PORTING_GUIDE.md` как эталонный flow.
- Последствия:
  - плюс: устойчивый процесс регистрации/recovery
  - минус: зависимость от внешнего сервиса телефонии
